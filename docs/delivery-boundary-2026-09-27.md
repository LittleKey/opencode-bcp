# BCP 交付职责与最小协议设计

状态：用户已确认设计方向并授权实施；具体接口和能力边界见 [delivery-integration-v1.12.md](delivery-integration-v1.12.md)。

原设计要求：“请现在设计交付考虑bcp应该做到哪一步”。后续授权：“你的设计方向是正确的，请按设计做完最后的实现”。授权范围为本文确定的职责边界。

## 1. 推荐终点

BCP 应做到：**让作者交付成为可读取、可定位版本、可核对来源归属的证据，并向编排方提供有依据的执行关联与明确的未知项。**

BCP 的成功条件是提供可以接受检查的证据，不是宣布任务通过验收。OMO 负责执行身份与生命周期，接收者负责结论是否满足任务；二者都不能把 BCP 的机械检查直接解释为语义通过。

下一步只增加必要的宿主关联与检查接口。现有四个模型工具、默认发布义务和作者归属规则继续使用。BCP 不接管任务调度，不建立第二套运行代次、重试预算和恢复状态机。

## 2. 设计依据

- 16 次同模型配对实验中，原提示与增加完成规则的提示均为 8/8 发布或复用，各 39 个 assistant 步骤。两组都明确授权发布，样本也小；结果不足以证明额外规则有收益，不能推导提示永远无效或漏发已消失。
- 已有机械留存解决了文件引用无保留版本的问题；v1.11.0 修正了无关路径、幂等重放和旧回调误清部分缺口的问题。其观察仍只覆盖有限宿主事件，不是权威运行关联。
- 只读漏发、外部写入、权限不足、来源不适用和结论遗漏，需要分别表达。统一的“交付成功”会掩盖这些差异。
- 裸路径快照只证明发布时读到的字节。正式评审还必须明确它实际检查的输入版本。

## 3. 职责分界

| 责任 | 负责方 | 承诺与边界 |
| --- | --- | --- |
| 结果、依据、适用范围和限制的表达 | 作者 | 对声明负责；无法完成时如实交付受阻结果 |
| 不可变记录、权限、幂等、导航与引用 | BCP | 已提交内容可按权限取回；不凭存在一个 ID 扩大权限 |
| 支持类型的版本留存与字节校验 | BCP | 返回确切版本和逐项检查结果；不支持的来源明确未验证 |
| 哪一次执行正在运行、结束、恢复或取消 | OMO／宿主 | 使用现有权威执行身份与生命周期 |
| 记录由哪次执行产生 | 宿主提供身份，BCP 接入校验 | 身份不可证明时保留未知，不根据最近记录、同名角色或相同 session 猜测 |
| 结论是否满足约束、是否覆盖所依赖内容 | 接收者 | 阅读原来源并判断；机械检查只能减少重复工作 |
| 是否启动依赖任务、请求修正或向用户裁决 | OMO／任务负责人 | 根据明确依赖和接收判断决定；BCP 不自行调度 |

记录作者身份、记录与执行的关联、正文所声称的原作者，是三个需要分别核对的事实。父角色保存咨询原文时，不能把自己的记录标成咨询者亲自发布的报告。

## 4. 最小交付内容

沿用现有 Outcome / Basis / Limits / Next 约定，不增加一套模型必填表单：

- **Outcome**：做成了什么、发现了什么，或被什么阻塞。
- **Basis**：实际依据、验证范围，以及所依赖的精确来源与工件版本。
- **Limits**：未验证事项、适用条件、缺失来源及冲突；与用户原话、作者解释分开。
- **Next**：影响后续使用的必要动作；没有后续要求时简短说明。

有代码、文档或报告时，记录是短索引，不复制工件正文。已有记录确实覆盖同一结果时复用，不为主角色转发、通知或每次检查再写同内容记录。父角色产生新的综合判断或决定时，以自己的身份记录新增内容。

受阻结果可以没有工件引用，但必须说明缺什么、据何判定和剩余不确定性。缺失文件、目录和猜测出来的版本不作为已核验工件。

## 5. 正常交付流程

1. **派发**：OMO 传递目标、原始约束、必要来源、被处理的版本和验收要求。终结交付仍要求发布或复用记录；明确的发布限制优先。
2. **固定依据**：作者优先读取已有提交或留存快照。正式评审没有可取回输入版本时，在允许范围内保留输入快照，或报告版本缺口；不等到评审结束后才把已变化的裸路径当成原评审对象。输入快照可由多份评审共用，不要求为快照再生成过程记录。
3. **产出与发布**：作者完成必要核验，提交或复用一份简短交付，回传完整引用。BCP 检查权限、记录载荷和支持的版本绑定；普通外部引用仍明确区分为未自动验证。
4. **结果传递**：宿主保持原执行结果和原文，附加候选交付引用及机械检查信息。前台返回、`task_result`、后台通知和恢复结果采用同一解释。
5. **接收核对**：接收者读取需要依赖的原记录，核对当前要求、版本、限制和权限。已核对的准确内容及版本仍在上下文中且无变化信号时，可以复用核对；否则重新读取。
6. **使用或报告缺口**：接收者确认可用后才将其作为后续依据。不可用时报告具体缺口，或在授权范围内重新验证并以验证者身份记录。一次交付可以只有部分结论可用，必须说明采用范围。

正常路径不新增模型轮次；复用当前上下文中仍有效的核对，不强制每跳重复读取和重新发布。

## 6. 薄关联接口

以下是设计要求的内部数据语义；具体字段与保守降级见实现契约，不增加模型工具：

| 数据 | 提供者 | 含义 |
| --- | --- | --- |
| 执行引用 | 宿主 | 能区分本次执行与此前重试、恢复的可信身份 |
| 候选记录引用 | 作者返回及宿主已验证的发布关联 | 供接收者核对；出现于文本中不等于已经被采用 |
| 归属检查 | BCP 与宿主适配层 | 本次执行产生、此前来源、或关联未确认 |
| 记录读取结果 | BCP | 按当前接收者权限可读、不可用或尚未检查；不泄漏隐藏流信息 |
| 工件检查结果 | BCP | 保留字节通过、检查不完整、外部引用未验证，或本次无工件 |

不返回综合的 `accepted=true`。来源可读与执行关联应逐条表达，不能由一个布尔值代替；候选记录齐全与否也不能仅凭数量判断。

### 6.1 身份与持久化

- 执行引用由宿主生成并从可信调用上下文传入，不让模型填写权威代次。复用 OMO 已有执行存储；BCP 不另建任务注册表。
- 发布可发生在执行结束前，因此不能要求一个尚未产生的终结版本号作为发布前提。宿主在取结果、发送通知时，用现有运行代次与终态修订检查过期结果。
- 发布记录保留原始作者与归属；引用旧记录只增加本次引用事实，不改变旧记录的原执行归属，也不自动证明适用性。
- 记录提交和宿主关联写入可能只有一侧成功。返回部分成功，不重复生成记录；重启后优先由已持久化证据重建。无法证明时保留未确认，不以时间邻近代替关联。
- 关联索引和检查同样受现有 scope、流隔离与接收权限约束。不得跨 scope 搬运记录或通过摘要泄漏独立评审内容。

现有 `publication_for` 用于补写时标识原执行／原消息，不直接改作通用运行标识。执行关联由宿主适配层承载；如实现确需扩展持久记录格式，须明确兼容旧记录、幂等载荷和迁移规则，不能悄然改变已有字段含义。

当前 v1.11.0 的输入 ID／消息关联观察器不满足上述权威关联要求。实现前先验证宿主能否提供稳定身份及三条主要返回路径；能力不足时停止在显式未确认，不用更复杂的启发式补齐承诺。

### 6.2 引用选择与检查

宿主从返回结果得到的 ID 只作为候选，即使它在本次执行中生成，也不能自动认定它是最终报告。接收者判断哪份记录覆盖要采用的结论。单纯 `board_get`、幂等重放、查询到一份最近记录，均不能直接升级成“合法复用”。

宿主只附加独立元数据，不改写作者原文或把执行成功改成运行失败。现行 §11.8 禁止自动改写子任务结果；实施该附加通道前，需明确修订它与原文保留的边界。缺少关联数据时，原始结果仍可查看，但不得由集成层自动标成已验收。

## 7. 缺口处理

| 场景 | BCP 应给出的事实 | 工作流处理 |
| --- | --- | --- |
| 正常编辑与发布 | 记录、版本和已知归属 | 接收者核对验证范围后使用 |
| 只读评审未发现问题 | 评审记录与实际被审版本 | 与有问题评审相同，不因 no-issues 免交付 |
| 文件不存在、任务受阻 | 受阻结论，可无工件 | 区分交付可读与业务未完成 |
| 作者漏发或漏回传 ID | 未找到已确认来源，或候选未确认 | 有界查找已有合格源；仍缺失时报告，不自动无限续聊 |
| 旧记录仍适用 | 原记录、原归属、当前可读性 | 接收者核对适用性后复用，不伪造本次新产出 |
| 评审后源文件变化 | 原输入版本与当前版本的差异或未知 | 旧评审不能直接覆盖新版本，必要时重新评审 |
| Council 等角色禁止写板 | 原作者独立发布能力受限 | 父角色可在授权范围保留有归属的原文并发布自己的综合报告；严格要求原作者报告时保留缺口 |
| 发布被明确禁止或来源无权读取 | 不可提供该来源 | 在允许范围答复并说明缺口，不为交付突破权限 |
| 重启、取消、旧通知或异常结束 | 可恢复的原记录和未确认关联 | 由宿主处理执行状态；无完成证据就不伪造完成 |

“有界查找”沿用已有索引和权限；只搜索与缺失对象相关的授权范围，不扫描全板、不生成新的模型恢复循环。需要原作者补写时由任务负责人显式决定，沿用现有恢复预算与作者身份限制。

## 8. BCP 的停止边界

BCP 不承诺模型每次主动调用发布工具，不自动判断需求覆盖、结论正确或风险可接受，不把提示词遵从率视作零漏发保证。

本方案不增加自动续聊、自动代写、后台审核 agent、自然语言依赖推断或最终回答阻断。若以后需要强制“某依赖未验收就不能启动”，应在 OMO 的显式依赖与执行策略中实现，并单独验证取消、失败和恢复路径。

直接用户任务仍适用当前默认发布或复用义务。优先完善跨上下文关联是实施顺序，不是给短任务、只读任务或直接回答增加豁免。直接任务漏发的保证边界继续如实披露。

## 9. 实施顺序与验收

| 次序 | 最小交付 | 验收条件 |
| --- | --- | --- |
| 1 | 保持现有存储、权限、快照、引用错误反馈及有限观察 | v1.11.0 现有回归不退化；提示词不因本提案继续扩张 |
| 2 | 验证宿主执行身份与接入能力，建立最小记录关联 | 同 session 的新执行、旧回调、恢复、重复事件和重启均不混淆归属；不具备能力时明确未知 |
| 3 | 将关联与逐项检查事实接入返回元数据 | 前台、`task_result`、后台通知一致；恢复结果兼容；不修改原文、不新增唤醒、不破坏独立席权限 |
| 4 | 小规模跨上下文验收 | 正常交付、合法复用、受阻、只读漏发、受限作者、缺引用和错版本分别有正确出口；接收者不把机械通过当语义通过 |

模型调用预算在具体实施前给定。正常路径目标为零新增模型请求、零新增模型工具；使用现有批量读取降低往返。记录缺口检测、错误归属、合法复用误报、重复发布、额外轮次与字节成本，按原始调用和来源记录复核，不以“日志没有告警”作为成功标准。

只有发现需要自动修复或强制门禁的独立证据，才扩大第 3、4 步以外的职责。设计文本不单独证明宿主能力、跨返回路径行为或端到端可靠性；这些结论须绑定实施后的具体源码与验收记录。
